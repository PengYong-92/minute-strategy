# 实时画像退化守卫设计

## 1. 背景

每日画像选择器使用最近 7 天观察样本，在每天 08:00 启用符合条件的完整画像。线上新样本表明，历史画像胜率不能稳定映射到启用后的实际表现：部分历史胜率高于 65% 的画像仍会在当日连续亏损，而部分历史胜率约 60% 的画像实际表现良好。

因此本次不提高全局画像胜率门槛，也不调整两笔并发上限。新增一个画像级实时退化守卫，在画像启用后根据该画像的实际已结算订单识别连续失效，并以冷却和基础金额试探恢复控制后续风险。

## 2. 目标与非目标

### 2.1 目标

- 按完整画像键和当前每日画像版本隔离实际订单序列。
- 同一画像连续亏损 3 单后立即进入冷却。
- 冷却结束后仅放行一笔基础金额试探单。
- 试探单盈利后恢复正常；亏损后重新冷却。
- 服务重启后仅依赖已有订单重建状态。
- 只暴露一个启动参数，避免与每日画像选择、方向连亏守卫混淆。
- 在 API、页面、观察记录和文档中提供可审计状态。

### 2.2 非目标

- 不修改 `DAILY_PROFILE_MIN_WIN_RATE=0.60` 或退出胜率线。
- 不修改 `MAX_OPEN_ORDERS=2` 和两分钟最小开单间隔。
- 不改变每日画像的 7 天统计、样本独立化或每日生效时刻。
- 不新增滚动胜率、EV、样本数等启动参数。
- 不使用观察订单结果触发正式订单守卫。
- 不强制关闭已经打开的订单。
- 不新增数据库表或单独持久化运行态。

## 3. 唯一配置

新增启动参数和环境变量：

```text
--profile-degradation-cooldown-minutes
PROFILE_DEGRADATION_COOLDOWN_MINUTES=60
```

- 默认值为 `60`，单位分钟。
- `0` 表示关闭实时画像退化守卫。
- 正数表示启用守卫并设置冷却时间。
- 负数归一化为 `0`。

以下规则固定，不作为启动参数：

- 连续亏损触发数：3 单。
- 统计范围：完整画像键 + 当前 `daily_profile_version`。
- 恢复方式：一笔基础金额试探单。
- 试探单未结算时：同画像继续阻断。

## 4. 数据范围

守卫只读取正式模拟订单，订单必须同时满足：

- `status == SETTLED`；
- `result` 为 `WIN` 或 `LOSS`；
- `profile_key` 等于当前信号的完整画像键；
- `daily_profile_version` 等于当前信号的画像版本；
- `settled_at <= current_time`。

排序使用 `(settled_at, id)`，确保重启和并发结算后的结果确定一致。不同方向、时段、策略族、策略标签或 DPS 版本之间不会共享连亏状态。

当前信号没有 `daily_profile_selected`、完整 `profile_key` 或 `daily_profile_version` 时，守卫不介入。

## 5. 状态机

### 5.1 DISABLED

冷却参数为 `0`。守卫不阻断订单，也不改变金额叠加。

### 5.2 NORMAL

当前画像最近连续亏损少于 3 单。订单继续遵守现有画像选择、订单策略、方向连亏、滚动优势、并发和金额叠加规则。

### 5.3 COOLDOWN

当前画像最近连续亏损达到 3 单，且：

```text
current_time < last_loss_settled_at + cooldown_minutes
```

当前信号返回 `PROFILE_DEGRADATION_BLOCKED`，并记录同来源观察信号。冷却时间从最近一笔连续亏损订单的结算时间开始计算。

### 5.4 RECOVERY_READY

画像已经触发连续亏损，冷却已结束，且触发后没有新的试探订单。下一笔通过其他守卫的同画像信号可以开单，但必须：

- 使用基础金额；
- 不消耗待用的 18U 滚单资格；
- 订单原因中注明“画像退化试探单”。

### 5.5 RECOVERY_PENDING

试探订单已经打开但尚未结算。阻断同画像的后续信号，避免同时产生多笔试探单。其他画像不受影响。

### 5.6 试探结算

- `WIN`：最近连续亏损归零，状态回到 `NORMAL`。
- `LOSS`：该亏损成为新的 `last_loss_settled_at`，重新进入完整冷却周期。

状态全部从订单序列推导。服务重启、进程恢复和历史订单加载后必须得到相同结论。

## 6. 决策顺序

实时画像退化守卫只处理已被当前每日画像正式选中的信号。接入顺序为：

1. 每日画像完整键匹配；
2. 现有订单策略检查，包括信号合法性、并发和最小间隔；
3. 波段批次守卫；
4. 实时画像退化守卫；
5. 现有方向结算序列守卫；
6. 滚动优势守卫；
7. 其他画像守卫；
8. 开单和金额分配。

画像级守卫放在方向级连亏守卫之前，使页面和观察记录优先显示更精确的阻断原因。任一前置规则已经阻断时，不改变原有决策码。

## 7. 金额叠加

`NORMAL` 状态保持现有两阶段金额逻辑。

`RECOVERY_READY` 状态调用开单逻辑时明确禁用本单金额叠加：

- 金额固定为当前配置的基础金额，不硬编码 10U；
- 不消费已有滚单资格；
- 不删除其他订单产生的滚单资格；
- 试探单盈利后仍按现有两阶段规则生成后续资格。

这样既保证试探风险固定，又不破坏其他画像的金额运行态。

正式订单 JSON 新增向后兼容字段：

- `profile_degradation_probe`：是否为画像退化试探单；
- `profile_degradation_triggered_at`：该轮退化触发订单的最后结算时间。

旧订单缺少字段时按 `False` 和 `0` 处理。守卫通过这些字段识别重启前已经打开或结算的试探单，不依赖原因文本反推运行态。

## 8. 状态与审计

`/api/state` 新增 `profile_degradation_guard`：

- `enabled`
- `status`
- `profile_key`
- `daily_profile_version`
- `consecutive_losses`
- `last_loss_settled_at`
- `pause_until`
- `cooldown_minutes`
- `probe_order_id`
- `reason`

页面状态区新增“画像实时守卫”，显示正常、冷却、待试探或试探待结算。订单原因展示试探标记。冷却和试探等待期间产生的观察信号使用 `PROFILE_DEGRADATION_BLOCKED`，便于后续统计被阻断信号的胜负。

## 9. 代码边界

新增独立模块 `app/profile_degradation_guard.py`，包含：

- 固定连亏常量；
- 配置归一化；
- 决策数据类；
- 无副作用的状态评估函数。

`MonitorState` 负责：

- 传入订单、当前时间和信号画像身份；
- 保存最近一次决策到快照；
- 记录阻断观察信号；
- 在试探开单时禁止金额叠加。

`server.py` 和 `scripts/run.sh` 只增加冷却时间一个参数。SQLite 继续通过订单 JSON 兼容保存，不增加 schema。

## 10. 错误与兼容处理

- 旧订单缺少画像键或画像版本时忽略，不误归类。
- 旧订单缺少试探标记时按普通订单处理。
- 结算时间缺失或晚于当前决策时间时忽略，避免未来数据泄漏。
- 冷却配置解析失败由现有命令行参数机制报错，不静默采用错误值。
- 旧数据库和旧画像选择快照无需迁移。
- 切换交易对时重新根据目标交易对订单计算状态。

## 11. 测试要求

### 11.1 纯函数测试

- 未选中画像时不介入。
- 少于 3 次连续亏损时正常。
- 连续 3 次亏损时冷却。
- 冷却截止毫秒时进入待试探，不多阻断一根 K 线。
- 历史盈利会重置连续亏损。
- 不同画像键和 DPS 版本互不影响。
- 试探订单打开后阻断同画像第二笔。
- 试探盈利恢复，试探亏损重新冷却。
- 乱序订单得到确定结果。
- 冷却参数为 0 时关闭。

### 11.2 状态集成测试

- 冷却命中返回 `PROFILE_DEGRADATION_BLOCKED` 并记录观察。
- 冷却期间不消费滚单资格。
- 试探单使用基础金额且不消费滚单资格。
- 试探单未结算时，同画像不能开第二笔。
- 其他画像仍可开单。
- 状态快照暴露完整守卫字段。
- 重启加载同一批订单后决策一致。

### 11.3 配置与页面测试

- 环境变量、命令行参数和中文帮助文本一致。
- 启动脚本参数只新增一个冷却值。
- 页面存在画像实时守卫状态元素。
- 前端能够格式化所有守卫状态。

## 12. 发布边界

本次实现完成后先运行聚焦测试、全量单元测试、Python 编译、JavaScript 语法和 Shell 语法检查。未经单独确认不清空模拟订单、不修改每日画像门槛、不修改并发上限，也不部署服务器。
